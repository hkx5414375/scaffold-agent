# ADR 0039: Python 组织成员管理

- Status: Accepted
- Date: 2026-09-01

## Context

Python 的 `organization-tenancy` `0.1.0` 已能创建组织、按成员关系授权并隔离业务数据，但还不能让第二个身份安全加入组织。若让不同 AI 在业务项目中临时实现邀请令牌、角色变更和最后管理员保护，不但重复消耗 Token，还容易保存邀请明文或产生并发条件竞争。

## Decision

1. Python 适配器支持 `organization-tenancy` `0.2.0`，保留 `0.1.0` 可选，并只新增 `000060_tenancy_members`；`000050_tenancy` 保持字节不变。
2. 管理员可以查看成员、创建邀请、变更角色和移除成员；普通成员只能查看当前组织成员。所有组织内接口复用已经验证的 `X-Organization-ID` 成员权限范围。
3. 邀请邮箱先规范为小写，72 小时后失效。创建响应只返回一次邀请明文，数据库只保存 SHA-256 摘要。
4. 接受邀请必须先完成身份认证，并且登录邮箱必须与邀请邮箱一致。不存在、过期、已接受、错误邮箱和错误令牌统一返回公开错误，避免泄露邀请状态。
5. 角色降级和成员移除先锁定组织行，再统计管理员数量。PostgreSQL 与 MySQL 的并发测试要求两个管理员同时降级时只能成功一个。
6. 成功和拒绝的邀请及成员变更，都在对应业务事务内写入安全审计；失败不能留下半条成员或邀请数据。
7. FastAPI 传输、稳定 OpenAPI、独立服务与仓储、SQLite 契约、PostgreSQL/MySQL 真库门禁和共用 `MembersView.vue` 作为同一个完整能力切片交付。

## Consequences

- Go、Java、Python 的成员协作 HTTP 与数据库安全语义一致，AI 可以直接按能力版本调用，不必阅读并重写底层实现。
- 旧项目可以继续锁定 `0.1.0`；升级到 `0.2.0` 不会修改已经执行的组织基础迁移。
- 组织所有权、改名、停用和重新启用继续属于后续 `0.3.0`，避免在成员版本中引入破坏性生命周期语义。
