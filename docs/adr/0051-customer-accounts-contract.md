# ADR 0051：顾客账户与会员生命周期契约

- 状态：Proposed
- 日期：2026-09-01

## 背景

商城顾客不是后台员工。若把公开注册账户直接写入后台 `identity_users`，顾客会被迫继承后台角色、权限和会话边界，不同 AI 还会重复设计邮箱规范化、密码策略、会话摘要、账户停用、跨租户隔离与防枚举错误，既浪费 Token，也容易产生越权。

## 决策

1. `customer-accounts` `0.1.0` 生成独立于后台身份系统的顾客账户、顾客会话、用例、管理接口和商城接口；它不创建后台角色，也不复用后台 Session Cookie。
2. 顾客邮箱统一去除首尾空白并转为小写，在当前组织范围内唯一。密码至少 12 个字符，使用与后台身份相同的有上限 PBKDF2-SHA256 算法，但保存在独立表中。公开登录失败统一返回相同错误；邮箱不存在时校验固定假摘要，账户停用或密码错误时仍完成真实摘要校验，避免通过文案或明显不同的计算路径泄露邮箱、账户状态或密码错误原因。
3. 顾客会话明文只通过 `HttpOnly`、`SameSite=Lax` Cookie 返回，数据库只保存 SHA-256 摘要；会话最长 30 天。登录、退出、修改密码、主动关闭账户和后台停用都会撤销相应会话。
4. 账户状态只允许 `active -> suspended -> active`，以及 `active -> closed`；`closed` 是终态。只有已登录的活跃顾客可以主动关闭自己的账户，`0.1.0` 不提供停用账户关闭入口。顾客可以修改姓名和密码；关闭后不删除主记录，以便后续订单保留稳定引用。
5. 后台读取和状态管理使用分离权限。后台停用、恢复以及顾客主动关闭必须在同一数据库事务内更新账户、递增乐观版本、撤销会话并写入审计事件；SQL 必须重复组织、状态和版本条件。
6. 启用组织租户时必须选择 `organization-tenancy` `0.3.0`。公开注册、登录和会话解析要求显式组织范围，并隐藏已停用组织与跨组织标识；Nuxt 只从服务端 `SCAFFOLD_ORGANIZATION_ID` 注入组织标识。
7. `0.1.0` 不伪造邮箱验证或密码找回。验证、找回、无密码登录和联合身份将在后续依赖通知能力的可组合版本中增加，且不得通过 HTTP 返回可用于接管账户的令牌。

## 影响

- AI 可以直接选择成熟的顾客身份边界，不必把后台 RBAC 改造成公开会员系统。
- 订单、购物车、优惠和支付能力可以引用稳定顾客 ID，同时保持匿名购物能力可独立组合。
- 本 ADR 只有在 Go、Java、Python、PostgreSQL、MySQL、共享 Vue 顾客管理和 Nuxt 注册/登录/账户页门禁全部通过后才改为 Accepted。
