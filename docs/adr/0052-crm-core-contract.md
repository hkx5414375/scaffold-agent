# ADR 0052：可组合 CRM 核心契约

- 状态：Accepted
- 日期：2026-09-02

## 背景

多数后台项目都会重复实现企业客户、联系人、跟进记录和销售机会。让不同 AI 临时生成这些表和状态机会导致字段、金额、租户隔离、审计、分页和销售阶段各不相同，也会重复消耗大量 Token。CRM 核心应是独立能力包，不依赖某个前端或模型，并且不能把“业务客户企业”误当作权限系统中的租户组织。

## 决策

1. 新增 `crm-core` `0.1.0`。它生成四种稳定实体：`crm_accounts` 表示业务往来的企业客户，`crm_contacts` 表示自然人联系人，`crm_activities` 表示不可变跟进记录，`crm_opportunities` 表示销售机会。它们与 `organization-tenancy` 的权限组织是不同概念。
2. 企业客户包含名称与 `active`、`archived` 状态；联系人包含姓名、可选企业客户、规范化邮箱、电话与 `active`、`archived` 状态。归档不删除记录，已经被活动或销售机会引用的标识保持稳定。
3. 跟进记录只允许 `note`、`call`、`email`、`meeting` 四种类型，必须引用当前范围内的企业客户、联系人或销售机会之一，并保存有时区的发生时间和有界摘要。`0.1.0` 不允许修改或删除已经写入的活动。
4. 销售机会必须引用企业客户，金额使用最小货币单位的有符号 64 位非负整数，币种规范为三位大写代码；金额和乐观版本在 JSON 中使用十进制字符串。阶段固定为 `lead`、`qualified`、`proposal`、`won`、`lost`，只允许向前推进，`won` 与 `lost` 是终态。
5. 所有列表使用最多 100 条的标识 Keyset 分页。所有可变实体使用乐观版本；成功写操作与审计事件在同一数据库事务提交。跨租户和不存在标识统一返回未找到，存储错误不暴露驱动细节。
6. 权限分为 `crm:read`、`crm:write` 与 `crm:pipeline:manage`。普通资料写入不能隐式推进销售阶段。生成服务不自动发邮件、不自动创建任务，也不把 CRM 联系人写入员工身份或商城顾客账户。
7. 与 `organization-tenancy` 组合时必须使用 `0.3.0`，所有 CRM 表都保存并重复校验当前权限组织标识；停用组织不能继续读写 CRM 数据。非租户项目使用单一空范围，但仍保留同一服务接口。
8. Vue 管理端只调用稳定 CRM HTTP 契约；后续营销、订单和支付能力通过稳定 CRM 标识组合，不直接修改 CRM 表。`0.1.0` 不实现自动线索评分、预测、邮件同步或第三方 CRM 导入。

## 影响

- AI 可以通过一个能力选择获得常用 CRM 主干，不再重复设计企业、联系人、活动和销售阶段。
- ERP、商城订单、营销和支付能力可以引用稳定 CRM 企业或联系人标识，但不会反向耦合 CRM 核心。
- Go、Java、Python 已分别通过 PostgreSQL/MySQL 生成、服务测试、数据库契约与共享 Vue 管理端门禁；三语言 OpenAPI、权限、Schema、迁移表和管理端一致性由自动化契约测试持续验证。
